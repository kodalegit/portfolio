Uwazo is a tax research assistant I built for tax professionals in Kenya. Users upload their own documents, and the assistant searches them alongside a shared library of tax law. Search runs on Postgres with the pgvector extension. Each document is split into chunks, and each chunk is stored as an embedding, a list of numbers that captures its meaning. A search finds the chunks whose embeddings are closest to the question's. A vector index makes that fast by searching approximately instead of comparing every row, which means it can miss some of the right chunks.

Early in development, retrieval was accurate. Then I added more documents, and the assistant started missing passages I knew were there. I switched the vector indexes from IVFFlat to HNSW, the problem went away, and I wrote it off as "IVFFlat needs reindexing when data grows".

I had no metrics from that time. To write this up properly, I rebuilt the setup and measured it. The measurements showed that my explanation was only partly right. They also showed a second problem that HNSW had hidden rather than fixed.

## The query

Every document search in Uwazo ran a query like this:

```sql
select e.content, 1 - (e.embedding <=> :query) as similarity
from document_embeddings e
join documents d on d.id = e.document_id
where d.deleted_at is null
  and d.user_id = :user_id
  and d.client_id is not distinct from :client_id
order by e.embedding <=> :query
limit 5;
```

It finds the five chunks closest to the question, but only among the current user's documents. The vector index speeds up the `order by`. The `where` clause decides which rows count.

The index came from an early migration, in the same file that created the table:

```sql
create index on document_embeddings using ivfflat (embedding vector_cosine_ops);
```

## Rebuilding the problem

I reproduced Uwazo's schema and query in a fresh pgvector 0.8.6 database on Postgres 17. For data, I used the 20 Newsgroups corpus, which has 20 topics. I split it into 19,375 chunks of about 120 words and embedded them on my laptop with bge-small-en-v1.5. That model produces 384-dimension vectors. Uwazo used 1536-dimension OpenAI embeddings, but the index behaves the same way.

I gave the chunks to 40 simulated users, each working on three topics, and added documents in four stages: 1,000, 3,000, 10,000 and 19,375 chunks. At each stage I ran 300 held-out questions against two copies of the table. One copy had IVFFlat, created on the empty table as in Uwazo. The other had HNSW.

To get the right answers, I computed the exact five nearest chunks for each question in NumPy. Recall is the share of those five that the database returned. A recall of 1.0 means the search found every correct chunk.

The scripts and raw results are <Experiment path="uwazo-pgvector">on GitHub</Experiment>, with instructions to run them.

## Finding 1: Postgres told me

Creating an IVFFlat index on an empty table prints this:

```text
NOTICE:  ivfflat index created with little data
DETAIL:  This will cause low recall.
HINT:  Drop the index until the table has more data.
```

Uwazo's migration would have printed the same notice. A notice does not fail a migration, so it went unnoticed.

IVFFlat works by grouping vectors into lists. When you build the index, it samples the table and picks one centre for each list, 100 lists by default. Every vector, then and later, goes into the list with the nearest centre. A query only scans the lists whose centres are closest to the question. By default it scans one.

On an empty table there is nothing to sample, so pgvector fills the centres with random numbers between 0 and 1. All of those centres point into the same narrow region, so they split real embeddings poorly. Every vector added later goes into a list chosen by those random centres. Related chunks end up spread across many lists, and a query that scans one list misses most of them.

At 1,000 chunks, the Postgres planner decided that reading the whole table was
cheaper than using the index. A full scan compares every row, so it returns
exact results. The broken index existed but was never used.

At 3,000 chunks, the planner switched to the index and recall fell to 0.53. At 10,000, it was 0.20. Almost half of the questions got back none of the five correct chunks.

So retrieval did not degrade slowly as data grew. It worked while the planner skipped the index, and broke when the planner started using it. That explains why my small development corpus never showed the problem.

## Finding 3: reindexing alone is not enough

My original explanation was "IVFFlat needs reindexing". I tested that at full size, with all 40 users, and compared it with the other settings.

| Setup at 19,375 chunks             | Recall, filtered by user | Recall, no filter |
| ---------------------------------- | ------------------------ | ----------------- |
| IVFFlat built empty                | 0.22                     | 0.26              |
| IVFFlat built empty, `probes = 10` | 0.77                     | 0.83              |
| IVFFlat rebuilt with data          | 0.44                     | 0.57              |
| IVFFlat rebuilt, `probes = 10`     | 0.91                     | 0.97              |
| HNSW, default settings             | 0.58                     | 0.99              |
| HNSW, `ef_search = 100`            | 0.86                     | 1.00              |
| HNSW, iterative scan               | 0.99                     | 0.99              |

Rebuilding the index with real data doubled recall, but it stayed low. The
default of 100 lists was too many for this table. With 19,375 rows, each list
held about 190 vectors, and scanning one list meant reading 1% of the data. The
pgvector docs suggest about one list per 1,000 rows and scanning about the
square root of the list count. Rebuilding and setting `probes = 10` brought
recall to 0.91.

Even then, IVFFlat needs care in an app where users upload documents every day. Its centres reflect the data at build time. As new topics arrive, the lists drift out of balance, and someone has to remember to rebuild the index and tune the settings.

HNSW has no build-time sample. It builds a graph and links each new vector into it as you insert. Without a filter, it kept recall above 0.99 at every size, with no tuning. That is why switching worked.

## Finding 4: HNSW has its own problem with filters

The first table also shows HNSW falling to 0.58 for the filtered query. At full size, two out of three questions got fewer than five results back.

The cause is the order of operations. HNSW finds the 40 nearest candidates by default, set by `hnsw.ef_search`. Postgres then applies the `where` clause. If a user owns 2.5% of the rows, about one of those 40 candidates belongs to them, and the query returns one or two chunks instead of five.

With only a few test accounts in development, nearly every row passes the
filter, so HNSW looks fully fixed. With many users, each owning a small share of
the data, the same symptom would have come back.

pgvector 0.8 added iterative index scans for this case. With `hnsw.iterative_scan = relaxed_order`, the index keeps searching until enough rows pass the filter. Recall stayed at 0.98 or above for every number of users I tested. Raising `ef_search` to 100 also helps, but only partly, because a smaller share per user needs a larger value.

## What I would do now

- **Create approximate indexes after the data exists, or use HNSW.** If a migration has to create an IVFFlat index on an empty table, plan to rebuild it once the table has real data.
- **Read migration notices.** The warning here was exact, and it named the fix.
- **Test retrieval at the size you expect to reach.** A small table lets the planner skip the index, so a small test can pass while the index is broken.
- **Check the plan.** `explain` shows whether a query uses the vector index. A test that passes on a sequential scan tells you nothing about the index.
- **Treat filtered vector search as a separate case.** Measure recall with filters as selective as your real ones. Per-user filters get more selective as the user count grows.
- **Turn on iterative scans for filtered HNSW queries.** Check your version with `select extversion from pg_extension where extname = 'vector'`. Relaxed order can return rows slightly out of order, so sort the final rows again by distance.
- **Keep a small recall test.** Exact nearest neighbours in NumPy for a few hundred questions take seconds to compute, and they turn "retrieval feels worse" into a number.

## Limits of this test

This is a reconstruction, not a measurement of the original system. The corpus is newsgroup posts, not tax law. The embeddings are 384 dimensions, not 1536. The users are simulated. Timings are not reported because, at under 20,000 rows, every setup answered in a few milliseconds. The mechanisms are general, though. Random centres from an empty build, a planner that skips the index on small tables, and filters applied after the index search all follow from how pgvector and Postgres work, and the numbers show the size of each effect.

</Limits>
